What drives the badge
One clock, three sources
The signals
lastActivity Strong
Server-verified, from Cheesetracker. The real "is playing" signal.
lastChecked Weak
The player's manual self-report on the tracker. We already sync this field on every status pass.
lastReported Weak New
Stamped when the player saves a note here. Weak by construction — it is the same kind of claim as lastChecked, just made in our UI instead of Cheese's.
The clock reads the latest of the three that is actually present.
When none of them is, the clock falls back to the room — mission.linkedAt, or tile.linkedAt on the map shell. An Unstarted slot is not unknown: the link going up is the moment everyone could have begun, so it is a real origin and the slot badges from it like any other. No room link yet means no clock and no badge, which is correct — there was nothing to start.
This is the one deliberate departure from stale()'s unknown-is-never-stale rule, and it is narrow: the fallback is an event we recorded, not the absence of one.
The thresholds
48h Caution. New constant — SLOT_CAUTION_HOURS. Deliberately the same 48h that already buckets a world as "Too Early" on the admin report, so the player's first nudge lands exactly when the host starts looking. For an Unstarted slot the two clocks share an origin as well — the report's elapsed clock runs from linkedAt too — so the caution appears in the same hour the world becomes report-eligible, and the report's unstarted Problem (which has no time gate of its own) fires against the same 48h.
72h Warning. Not a new constant — reuse PROBLEM_STALE_HOURS, which is already 72. That keeps one number in one file, and makes the badge an honest preview of the report's stalled problem rather than a second opinion.
Where the note is written
Mission slots are server-write-only, so a casino note takes a new callable alongside setMissionParticipantStatusNote — same auth shape, indexed by slot. It writes note and lastReported in one update, and it must reject a slot the caller does not own.
Tile slots (map shell) need no callable: the adventurers/$advId rule already lets an owner write their own subtree. They do need a .validate for the note shape, mirroring the one guarding the existing statusNote.
Notes live on the slot. The existing per-participant statusNote is a seat-wide note and stays as it is — a five-card seat could never say which game it meant, which is the gap this closes.
Three things to watch
Adding lastReported to the report's stamps array is a one-line change with real teeth: a note now clears the stalled Problem — which is the point of restoring notes, but it is worth saying out loud before shipping. The noActivity warning is untouched: it reads lastActivity only, and a note must not launder a dead slot.
Both sync paths write leaf fields, so notes survive a status sync. Two writers do not: resubmitCasinoYaml's card re-pick rebuilds slots through cardsToSlots, and adminSetParticipantSlots replaces the array wholesale. The re-pick only happens while forming or on a deny, so little is lost — but the admin editor should carry notes across.
A note is a self-serve excuse — it clears the incident whether or not the player played. That is not new: lastChecked already does exactly this from the tracker side, and the note is the better door because it says why. But nothing catches a persistent note-writer who never plays except noActivity, which is an admin-facing Warning costing no incident.
